POINT 4 - REGRESSION CONFIRMEE, ET C002 EST COSMETIQUE. Cause racine trouvee: `_actes_store._forme_comparable` compare le texte du code, `CREATE VIEW IF NOT EXISTS v_actes AS ...`, a ce que SQLite range dans sqlite_master, `CREATE VIEW v_actes AS ...` - SQLite supprime la clause IF NOT EXISTS. Les 10 vues du module la portent. Mesure sur une base saine, fraichement preparee: `vues_perimees` rend 11 vues sur 11 perimees. Toujours. Preuve du diagnostic: en neutralisant la seule clause IF NOT EXISTS, la meme base rend 0 perimee, et apres un DROP rend exactement ['v_matrice_gouvernance'].

Consequences mesurees sur le code livre:
(a) chaque `lire_vue` DROP et re-CREATE les 11 vues: une lecture est devenue une ecriture, sans condition;
(b) base en lecture seule -> OperationalError "attempt to write a readonly database" (l'ancien code lisait);
(c) un autre processus tenant un verrou -> OperationalError "database is locked" (l'ancien code lisait);
(d) 20 appels a matrice() = 5,5 s, soit ~275 ms par ecran de pur brassage de DDL.
(e) le mecanisme que la correction porte en titre - "comparaison du texte de sqlite_master avec les VUES du code" - ne discrimine jamais rien. Ses deux tests passent pour la mauvaise raison: "on reconstruit toujours" donne accidentellement la bonne reponse. Aucun test n'affirme le cas negatif (base saine -> 0 perimee); le seul test qui touche `vues_perimees` fait un assertIn, jamais un assertEqual([]).

Le correctif tient en une ligne dans `_forme_comparable`. Mais tant qu'il n'est pas applique, il ne s'agit pas d'un realignement detecte: c'est une reconstruction inconditionnelle du schema a chaque lecture, et elle casse deux chemins qui fonctionnaient.

## Regressions relevees (6)

- Une lecture est devenue une ecriture inconditionnelle. `lire_vue` appelle `rafraichir_vues`, et comme `vues_perimees` juge toujours les 11 vues perimees (cause racine: IF NOT EXISTS), chaque lecture DROP et re-CREATE les 11 vues. Mesure: base en lecture seule -> OperationalError 'attempt to write a readonly database'; base tenue par un verrou exclusif concurrent -> OperationalError 'database is locked'. Les deux cas fonctionnaient avant. Cout: ~275 ms par appel a matrice(), 5,5 s pour 20. Aucun test ne couvre ces deux chemins.

- Debordement de zone sur la couche partagee `server/src/coproscope/vault/gouvernance_store.py`, et conflit direct: `chantier/fix-registre` modifie le MEME fichier. Chevauchements supplementaires a arbitrer avant integration en serie: _actes_schema.py (fix-vues + fix-registre + 096-1), _actes_store.py (fix-vues + 096-1 + 096-2), _actes_constats.py (fix-vues + 096-1 + 096-2), _actes_vues.py (fix-vues + 096-1).

- `gouvernance_store.lire` leve desormais `SchemaDeGouvernanceDivergent` pour toute OperationalError autre que 'no such table'. Verifie: AUCUN appelant ne l'attrape - web/resolutions_view.py, _convocation_store.py, _convocation_registre.py, lisibilite.py, pont_actes.py, _pont_actes_source.py, _resolutions_registre.py. Une derive de schema devient donc une exception non rattrapee sur des ecrans qui appartiennent a d'autres zones, sans un test dans ces zones. Le choix 'faire du bruit' est defendable et conforme a la consigne; le fait que le bruit sorte en 500 chez les voisins doit etre un arbitrage du coordinateur, pas un effet de bord.

- `remplacer_pour_documents` change sa valeur de retour (nombre de cles distinctes au lieu du nombre soumis) dans la couche partagee. Correct pour C044, mais les journaux de traitement des convocations et des resolutions - zones voisines - rapporteront desormais un autre nombre, sans test dans ces zones.

- `_verifier_cle` est appele depuis `ensure_schema` pour TOUTE table, dont `resolutions` (CLES_RESOLUTIONS). Il signale correctement le risque pour actes_autorisation (aucune base d'instance ne porte encore ces tables) mais pas pour `resolutions`, ou des bases locales existent deja. Une base dont la cle primaire de `resolutions` differe de celle du code fait desormais lever a l'ecriture. A verifier sur une base reelle avant integration - inspection du seul PRAGMA, pas des donnees.

- Point de doctrine a soumettre a Brice: son C029 supprime le retrait de CTRL_AVIS_CS sur la designation du syndic, sur lecture de LEGIARTI000039313574. Le changement est substantiel - il fait passer une portee de 3 a 4 controles exigibles, donc il cree des manquements affiches a des coproprietaires. La lecture est plausible, mais elle merite une seconde relecture juridique tracee avant integration, pas la seule parole du correcteur.
